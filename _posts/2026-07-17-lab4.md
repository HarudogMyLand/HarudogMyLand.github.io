内核态的运行逐步趋于完善，Lab4不再继续添加大型的数据结构。内核态完善了，用户态怎么办？用户态目前仍是一片空白，尽管我们能编写一些裸机代码（`bare`中），期望的C语言代码还是无法实现。

## 系统调用

在 MIPS 4KC 架构中，CPU 的运行状态由 CP0 协处理器的 Status 寄存器控制（如果你没忘记 Lab3）：

- **UM (User Mode) 位**：置 1 时表示处于用户态，置 0 时表示内核态。
- **EXL (Exception Level) 位**：发生异常时硬件自动置 1，强制 CPU 进入内核态并屏蔽中断。

一个完整的系统调用，需要跳出用户、陷入内核。其完整的调用关系如下：

```text
(User Space)
 printf / debugf
  └── syscall_print_cons
       └── msyscall
            └── syscall
 ----------------------- Trap -----------------------
 (Kernel Space)
 exc_gen_entry
  ├── SAVE_ALL (Trapframe)
  └── j handle_sys (8 号处理程序)

 handle_sys (kern/genex.S)
  └── do_syscall
       ├── syscall_table
       ├── sys_print_cons / sys_mem_alloc
       └── Trapframe $v0 
        ↓
 ret_from_exception (eret 返回用户态)
```

在这个过程中，最核心的问题是：**用户态和内核态使用的栈是隔离的，参数如何传递？**

回想一下，我们在编写裸机MIPS程序的时候，使用系统调用的过程：

```mips
li $v0, 1
add $a0, $t0, $zero
syscall
```

CO裸机编程中，我们会将参数存储在`a0-a5`寄存器，将系统调用号存在`v0`寄存器中。但MIPS 4KC有着不同的 MIPS 的函数调用规范。MIPS 规定：

1. 函数的前 4 个参数存放在 \$a0 - \$a3 寄存器中。
2. 第 5 个及之后的参数通过栈传递（且调用者需在自己的栈帧底部为前 4 个参数预留 16 字节的“参数保留区”）。

`msyscall` 函数最多接收 6 个参数：第 1 个参数是**系统调用号（sysno）**，保存在 $a0 中；后 5 个参数是传递给内核的具体数据。

```c
// syscall_lib.c
int syscall_print_cons(const void *str, u_int num) {
	return msyscall(SYS_print_cons, str, num);
}

// syscall_wrap.s
LEAF(msyscall)
	syscall
	jr ra
END(msyscall)
```

`msyscall`是一个叶子函数，直接调用`syscall`陷入内核异常处理程序并通过`handler`转到异常处理函数`do_syscall`。

### `do_syscall`

`do_syscall`函数首先声明一个函数指针，用于之后转到相应的`syscall`调用。调用一个`tf->cp0_epc+=4`将返回的入口移动到下一条指令。

接下来，`do_syscall`接下来会从`a0`寄存器读取系统调用号并分发到`func`函数，并将其余三个寄存器与栈上的两个参数读取出来使用

```c
tf->regs[2] = func(arg1, arg2, arg3, arg4, arg5);
```

跳转到目标`syscall`函数并将返回值保存到`v0`寄存器。

### 实现系统调用函数

系统调用函数并没有什么特别，由于我们已经进入内核态，系统调用函数实际上就是通过运用我们之前lab2与lab3学过的函数帮助用户态实现他们无法实现的功能。

内核态系统调用一般有以下几个流程：

1. 合法性检查
2. 从全局数组或暴露的结构中获取PCB等结构体
3. 执行

第2步中，我们一般不是获得进程PCB就是获得物理页结构体。`envid2env`函数负责将传入的`envid`转换为`env`结构体。特别的是，`envid2env`函数传入了一个`checkperm`，为1时函数会检查当前环境是否有权限访问目标环境（判断传入的`e`进程是不是`curenv`自己或其子进程）。

#### 三个示例系统调用函数

`sys_mem_alloc`、`sys_mem_map`和`sys_mem_unmap`是我们需要添加的系统调用函数。

三个函数作用分别如下：

1. 该函数使用`page_alloc`与`page_insert`，在用户态看来这个就是申请了一批内存
2. 该函数使用`page_lookup`与`page_insert`，将`srcenv`的`va`地址处的物理页映射到`dstenv`的`va`地址
3. 该函数使用`page_remove`删除该映射。

## 进程间通信

进程间通信（IPC）非常重要，如果你认真听了理论课一定会非常恼火。管道、信号量、共享内存等等都是进程间通信。然而，我们的MOS有一个投机取巧的方法。

在实际操作系统中，**不应该**像MOS 或者 JOS 那样直接将 `ENVS`和 `PAGES`完整地映射到用户地址空间。但是我们为了教学，将他们暴露在了`UEXSTACKTOP`上方的内存区域内。因此，进程只需要通过访问暴露出的这个PCB区就能进行通信。

在`Env`结构体中，添加了以下专门用于进程通信的字段

```c
struct Env {
// lab 4 IPC
    u_int env_ipc_value;
    u_int env_ipc_from;
    u_int env_ipc_recving;
    u_int env_ipc_dstva;
    u_int env_ipc_perm;
};
```

| 字段 | 含义 |
| ---- | ---- |
|   `env_ipc_value`   |  进程传递的具体数值    |
| `env_ipc_from env_ipc_dstva` |发送方的进程ID |
|`env_ipc_recving` |1：等待接受数据中；0：不可接受数据 |
|`env_ipc_dstva`|接收到的页面需要与自身的哪个虚拟页面完成映射|
|`env_ipc_perm` |传递的页面的权限位设置|

为了操作这些字段，我们添加两个系统调用：`sys_ipc_recv`和`sys_ipc_try_send`。

### 进程间通信调用

**`sys_ipc_recv`**

进程间通信时，这个函数应当先调用，将自己的`env_ipc_recving`字段置为1，`env_ipc_dstva`的值设置为自己的虚拟地址，随后将自己阻塞，从而主动放弃CPU。

**`sys_ipc_try_send`**

接收方准备好接受信息之后，发送方开始传输自己的信息。首先对`srcva`与`envid`做合法性检验并得到相应变量。接着手动修改接收方的IPC字段：

```c
	e->env_ipc_value = value;
	e->env_ipc_from = curenv->env_id;
	e->env_ipc_perm = PTE_V | perm;
	e->env_ipc_recving = 0;
```

最后将接收方状态设置为可运行，并插入调度队列尾部。

> 值得一提的是，由于在我们的用户程序中，会大量使用 srcva 为 0 的调用来表示只传 value 值，而不需要传递物理页面，换句话说，当 srcva 不为 0 时，我们才建立两个进程的 页面映射关系。因此在编写相关函数时也需要注意此种情况。

所以最后只有在`srcva != 0`时才调用`page_insert`插入新的页面。

## `fork`

如何创建一个新进程呢？Linux与Unix的回答是`fork`。

创建一个进程是操作系统内核的功能，为了让用户享受到这个功能，我们实现了`fork-exec`。`fork`系统调用完全克隆一个当前进程，在子进程中返回0，父进程中返回子进程id来区分。`exec`系列函数会夺舍当前进程为一个完全不同的进程。

> 若在进程中调用exec，进程的地址空间（以及在 内存中持有的所有数据）都将被重置，新程序的二进制镜像将被加载到其代码段，从而让一个从 头运行的全新进程取而代之。

```c
// A example of using fork
	int ret = fork();
    if (ret == 0) printf("I am child!\n");
    else printf("I am parent!\n");
    return 0;
```

`fork`的实现在`user/lib/fork.c`中，他以及之后的COW异常的调用关系大致如下

```text
fork() (user/lib/fork.c)
  ├── sys_set_tlb_mod_entry (设置父进程自身的页写入异常处理入口)
  ├── sys_exofork (陷入内核，分配 PCB，复制上下文)
  │    └── (内核中：子进程 Trapframe 的 $v0 被强行置为 0)
  ├── [如果返回非 0，即父进程继续执行]
  │    ├── 遍历用户地址空间页表项
  │    │    └── duppage (按页面权限进行共享/只读/COW映射)
  │    ├── sys_mem_alloc (为子进程分配一块全新的 UXSTACK 异常栈)
  │    ├── sys_set_tlb_mod_entry (设置子进程的页写入异常处理入口)
  │    └── sys_set_env_status (将子进程状态置为 ENV_RUNNABLE，加入调度队列)
  └── [如果返回 0，即子进程开始执行]
       └── 更新 thisenv 指针，返回


 (用户进程对 PTE_COW 页面执行 store 指令，因缺少 PTE_D 触发 TLB Mod 异常)
        |
       \|/
 [硬件异常陷入内核] exc_gen_entry -> handle_mod -> do_tlb_mod 
  ├── 计算用户异常栈指针 (UXSTACKTOP 或当前异常栈向下扩展)
  ├── 将当前的现场 Trapframe 复制到用户异常栈上
  ├── 修改原 Trapframe 的 EPC 指向 env_user_tlb_mod_entry 
  └── 修改原 Trapframe 的 $a0 寄存器指向压入异常栈的 Trapframe
        |
       \|/
 [内核 eret 返回用户态，CPU 跳转至 cow_entry 执行]
 cow_entry (user/lib/fork.c)
  ├── 检查 cp0_badvaddr 对应的页表项是否含有 PTE_COW
  ├── sys_mem_alloc (在临时地址 UCOW 处分配一个新的物理页)
  ├── memcpy (将发生异常的页面的内容复制到 UCOW)
  ├── sys_mem_map (将新分配的物理页映射回原虚拟地址，并恢复 PTE_D，取消 PTE_COW)
  ├── sys_mem_unmap (解除临时地址 UCOW 的映射)
  └── sys_set_trapframe (将 CPU 状态恢复为异常栈中保存的 Trapframe，重新执行写入指令)
```

`fork` 的核心是复制当前进程，但是如果我们在内核中完全拷贝父进程的所有物理页，不仅耗时，而且极其浪费——因为实际操作中子进程经常在 fork 后立即调用 exec 执行新程序，刚才复制的数据瞬间作废。

因此我们只复制上下文和页表，不复制实际的物理内存页。

**`sys_set_tlb_mod_entry`函数**

这个函数声明如下：

```c
int sys_set_tlb_mod_entry(u_int envid, u_int func);
```

他将`envid`进程的`env_user_tlb_mod_entry`设置为传入的函数指针，`fork`中填写为`cow_entry`。

**`sys_exofork`函数**

`sys_exofork` 和我们在 Lab3 写的 `env_alloc` 非常相似。实际上他直接调用了`env_alloc`。关键区别在于：

1. 我们需要将当前进程（保存在内核栈顶）的 `Trapframe` 完整地 `memcpy` 给新分配的子进程控制块的 `env_tf`。
2. 返回值控制：系统调用的返回值存放在 v0 寄存器中。我们要手动将子进程 `env_tf` 中的 v0 寄存器修改为 0。这样，当子进程未来某刻被调度器选中并恢复上下文时，它会“认为”自己刚从 `syscall` 返回，且返回值为 0。

最后，`sys_exofork`将自己设置为`NOT_RUNNABLE`状态并返回进程id：现在这个子进程还没有加入队列，纯粹是父进程凭空造出来的一个控制块，随后父进程带着子进程id返回。

**`env=envs+ENVX(syscall_getenvid())`**

```c
	child = syscall_exofork();
	if (child == 0) {
		env = envs + ENVX(syscall_getenvid());
		return 0;
	}
```

父进程获得了子进程id之后，会直接跳过这一段程序，继续为子进程设置页表与内存。多个时间片后，子进程苏醒从`syscall`返回，发现自己的返回值是0，`child`字段是0，因此执行`env=envs+ENVX(syscall_getenvid())`。

其中，`env`是`const volatile struct Env *env`，这是一个定义在用户空间的**只读全局指针**，指向**用户程序**自己的进程控制块。

当子进程苏醒并执行到这里时，我们需要回顾一下内存状态：由于子进程完全继承了父进程的数据段（此时还在触发 COW 机制前，完全指向同一块物理内存），子进程的全局变量 env 里存储的值，仍然是指向父进程 PCB 的地址！因此子进程必须更新`env`指针。

**准备地址空间**

> 此外，父进程还需要将地址空间中需要与子进程共享的页面映射给子进程，这需要我们遍历 父进程的大部分用户空间页，并使用将要实现的`duppage`函数来完成这一过程。`duppage`时，对 于可以写入的页面的页表项，在父进程和子进程都需要加上PTE_COW标志位，同时取消 PTE_D 标志位，以实现写时复制保护。

```c
	for (i = 0; i < VPN(USTACKTOP); i++) {
		if (vpd[i >> 10] & vpt[i] & PTE_V) {
			duppage(child, i);
		}
	}
```

按照指导书的指示，异常栈与全局区的内存不应当复制或COW。

> 异常栈绝对不能共享或写时复制！想象一下，如果异常栈被设为 COW，当进程发生“页写入异常”试图向异常栈压入现场时，又触发了一次“缺页异常”，这会导致内核发生无穷无尽的死锁与崩溃。因此，循环在 `USTACKTOP` 戛然而止，父进程后续会为子进程单独 `alloc` 一页全新的异常栈。

`if`条件中的判断完全依赖于自映射机制。我们知道`i`代表虚拟页号，高十位是PDX，低十位是PTX，此处的`vpd[i>>10]`就代表页目录项有效，`vpt[i]`就代表页表项有效。

实际上，更正确的写法应该是`(vpd[i>>10] && PTE_V) && (vpt[i] && PTE_V)`，防止逻辑判断出问题。只要我们判断这个页面有效，就COW这个页面

**`duppage`**

`duppage`接受两个参数，子进程的`envid`和需要复制的`vpn`。

首先，`duppage`需要：

1. 取出当前这个页面的权限位（Permission Bits）。
2. 根据不同的权限情况，在父进程和子进程的页表中建立相应的映射关系。

```c
	addr = vpn << PGSHIFT;
	perm = vpt[vpn] & 0xfff;
```

这里我们又一次使用了神奇的自映射指针，获取了页表项低12位的权限位`perm`。

-> 分支 A：可以直接复制的页面

在这一步，我们需要判断一个页面是否需要被设置为“写时复制”。这三个条件涵盖了所有**不需要**进行权限改造的特例：

1. `(perm & PTE_D) == 0`：页面本来就**不可写**（没有 Dirty 权限，比如代码段）。既然父子进程都不能写，那直接共享一块物理内存就好，没有任何数据被篡改的风险。
2. `(perm & PTE_LIBRARY)`：这是一个**库共享页面**。这种页面在设计上就是用来被多个进程共同读写的，父子进程对它的修改理应相互可见。因此，必须保留它的 PTE_D 可写权限，让两边都能随意操作。有关`PTE_LIBRARY`的内容将在后续实验中提及。
3. `(perm & PTE_COW)`：这是一个**已经是写时复制**的页面。这种情况通常发生在“多代繁衍”（例如父进程 fork 出子进程 A 后，又 fork 出了子进程 B）。对于这个已经在上一轮被剥夺了 `PTE_D` 并打上 `PTE_COW` 烙印的页面，直接按原样把这种状态传递给新的子进程即可。

如果满足以上任意一点，父进程直接发起系统调用 `syscall_mem_map`。
这里传入的参数非常有意思：`syscall_mem_map(0, addr, envid, addr, perm)`。

- 参数 0 表示源进程为当前进程（即父进程自己）。

> ```神金
> 1 内核啊，你当侧耳听我的祷告。
> 2 看哪，在我所居之地，那名为addr的所在，有一张物理的页。
> 3 求你将它迁移到你仆人的居所，那仆人的名字叫做envid，他的宅邸也在addr之处。
> 4 并且保守那称为perm的权柄，使它全然不变，一如从前。
> 5 愿这事成就，如同你的旨意行在地上。阿们。
> ```

-> 分支 B：写时复制

```c
else {
    // 步骤 B1：修改权限位
    perm = ((perm & ~PTE_D) | PTE_COW);
    // 步骤 B2：将修改后的权限映射给子进程
    r = syscall_mem_map(0, (void*)addr, envid, (void*)addr, perm);
    if (r < 0) user_panic("user panic mem map error");
    // 步骤 B3：重新将修改后的权限映射给父进程自己
    r = syscall_mem_map(0, (void*)addr, 0, (void*)addr, perm);
    if (r < 0) user_panic("user panic mem map error");
}
```

如果代码走进了 else，说明这是一个普通的、父进程正在使用且可写的页面,如普通的数据段或栈）。

**步骤 B1：更新权限位**

`perm = ((perm & ~PTE_D) | PTE_COW);`

这是一招非常经典的位操作：

- `~PTE_D` 对可写标志位取反，变成了该位为 0，其余为 1 的掩码。
- `& ~PTE_D`：无情地剥夺了该页面的底层硬件可写权限。
- `| PTE_COW`：贴上一个软件维度的标签。内核与操作系统会在需要写的时候分配新页面。

**步骤 B2 与 B3：顺序？**

代码注释有一个问题：

> The page should be first mapped to the child before remapped in the parent. (Why?)

为什么必须要**先调用系统调用映射子进程，然后再重新映射父进程自己？**

假设我们反过来做，**先重映射父进程**（剥夺了父进程的 PTE_D），**再映射子进程**，会发生什么？

1. 父进程执行了 `syscall_mem_map`，把自己的页面变成了只读的 COW 页。
2. 就在此时，在调用第二个 `syscall` 映射子进程之前，时钟中断发生了（我们的`fork`是用户态函数啊！），操作系统把 CPU 切走了！
3. CPU 切回父进程，但还没走到映射子进程的代码时，父进程突然想往这个 `addr` 写个数据[^1]。
4. 因为该页现在对父进程已经是 COW 了，于是触发了页写入异常。内核蹦床跳转到异常处理程序，分配了一个**新的物理页**给父进程，并把原数据拷了过去，父进程对新页面写入了数据。
5. 父进程异常处理结束，继续执行代码，走到了原本的第二步，开始将当前地址 `addr` 映射给子进程。
6. **COPY ON DOOM**：此时父进程要分享给子进程的，是刚刚新分配的物理页（里面包含了父进程写的新数据）！而子进程本应该继承的是 fork 发生那一刻旧物理页的数据。
7. 子进程由于父进程中途发生了一次缺页异常，意外地获取了不该拥有的、发生在 fork 之后的新数据，违背了 fork 的快照语义！

所以，正确的做法是：

**先映射子进程**。此时这个物理页对子进程是只读的。虽然父进程此时还是可写的，但因为代码依然在执行父进程的系统调用流程中（这里父进程不会突然去写那个特定的数据页），紧接着父进程立刻发起第二次系统调用，**重映射自己**。

只有当父子双方的页表都被写入了 `PTE_COW` 后，这个写时复制的陷阱才算真正布置安全。

最后，调用系统调用设置处理tlb的函数为`cow_entry`，并将进程设置为可运行状态，`fork`成功结束。

## 写时复制异常

在传统的宏内核中，缺页异常触发后，内核会负责所有错误处理：查表、分配物理页、拷贝数据、修改页表、返回用户态。

而在我们简化的 MOS 操作系统中，内核并不负责页面的拷贝工作。它仅仅充当一个“**蹦床（Trampoline）**”，将异常捕获后，“弹射”回用户态，由用户进程自己去完成页面的复制与映射。

```text
 (用户进程对 PTE_COW 页面执行 store 指令，因缺少 PTE_D 触发 TLB Mod 异常)
        |
       \|/
 [硬件异常陷入内核] exc_gen_entry -> handle_mod -> do_tlb_mod 
  ├── 计算用户异常栈指针 (UXSTACKTOP 或当前异常栈向下扩展)
  ├── 将当前的现场 Trapframe 复制到用户异常栈上
  ├── 修改原 Trapframe 的 EPC 指向 env_user_tlb_mod_entry 
  └── 修改原 Trapframe 的 $a0 寄存器指向压入异常栈的 Trapframe
        |
       \|/
 [内核 eret 返回用户态，CPU 跳转至 cow_entry 执行]
 cow_entry (user/lib/fork.c)
  ├── 检查 cp0_badvaddr 对应的页表项是否含有 PTE_COW
  ├── sys_mem_alloc (在临时地址 UCOW 处分配一个新的物理页)
  ├── memcpy (将发生异常的页面的内容复制到 UCOW)
  ├── sys_mem_map (将新分配的物理页映射回原虚拟地址，并恢复 PTE_D，取消 PTE_COW)
  ├── sys_mem_unmap (解除临时地址 UCOW 的映射)
  └── sys_set_trapframe (将 CPU 状态恢复为异常栈中保存的 Trapframe，重新执行写入指令)
```

**`do_tlb_mod`函数**

为了防止将现场压栈时，发现栈的页也是COW导致异常叠加，我们在用户态预留了一个特殊的栈：`UXSTACK`，用户异常栈，父子间永远独立，永远可写，不属于COW。

首先，`do_tlb_mod`将内核栈上的`tf`保存到临时`tmp_tf`中用于交给之后用户态的`cow_entry`。

接下来，如果：

- 发生异常时，用户正在使用普通栈（`$sp < USTACKTOP`），那么条件成立。内核强制将接下来的目标栈顶设为异常栈的最高处（UXSTACKTOP）。

- 发生异常时，用户已经处于异常栈区间（即正在执行 `cow_entry`，触发了二次缺页），条件**不成立**。此时代码跳过 if，直接保留发生异常那一刻的 `$sp`。
- **分配空间**：随后，无论上述哪种情况，都执行减法操作，在选定的栈顶向下开辟出一个 `Trapframe` 大小的空间。

随即，调用

```c
*(struct Trapframe *)tf->regs[29] = tmp_tf;
```

我们将刚刚计算出的用户异常栈地址（tf->regs[29]）强转为 `Trapframe` 指针，然后把第一步备份的现场 `tmp_tf`，强制地砸在用户异常栈上。

至此，用户态有了恢复现场所需的所有数据。

```c
	if (curenv->env_user_tlb_mod_entry) {
		tf->regs[4] = tf->regs[29];
		tf->regs[29] -= sizeof(tf->regs[4]);
		tf->cp0_epc = curenv->env_user_tlb_mod_entry;
	} 
```

最后，向`a0`传入`tmp_tf`，在栈上预留空间并确定返回地址。回到`cow_entry`函数。

**`cow_entry`函数**

最后的`cow_entry`函数只有一个任务：在用户态，用系统调用，分配一个新页。

涉及到的系统调用正好是我们之前填写的：

`sys_mem_alloc`，`sys_mem_map`，`sys_mem_unmap`。

1. 检查`tf->cp0_badvaddr`（记作`va`）的权限位，没有`COW`就报错
2. 将`COW`改为`PTE_D`
3. 向我们约定的`UCOW`位置分配一个新页
4. 把`va`一页的内容复制到`UCOW`，然后将这个物理页共享给`env`的`va`，现在`va`指向新地址`UCOW`对应的物理页
5. 取消`UCOW`映射，现在`va`映射一个可写的物理页了！

最后，我们调用了一个专门的系统调用 `syscall_set_trapframe`，把保存在异常栈上的那个案发现场 `tf` 原封不动地交还给内核。
内核接收到这个`tf` 后，将其直接覆盖到当前的寄存器上下文中，并再次执行 `eret`。

随着 `eret` 的执行：

- CPU 恢复了引发异常那一瞬间的各个寄存器值。
- PC 指针回到了那条曾经失败的 store 写入指令。
- **但是，这一次一切都不一样了。** store 指令面前是已经挂载好新物理页、开启了 PTE_D 的可写内存。
- 写入指令顺利执行，程序继续往下跑，进程对刚刚经历的这场惊心动魄的错误处理一无所知。

一切就此结束。

## 一些补丁



- **UCOW (写时复制的跳板地址)**

  - **它是做什么的？** cow_entry 中用来挂载新分配的物理页的临时虚拟地址。
  - **深层思考：为什么可以固定用这一个地址？** 在支持多线程的现代操作系统中，如果两个线程同时发生 COW 异常，固定跳板地址会导致数据覆盖。但在我们的 MOS 实验中，用户进程是**单线程**的。硬件异常是同步阻塞的，当前进程处理完这一个缺页异常之前，绝对不可能再并发触发第二个需要使用 UCOW 的异常。因此，系统直接在内存布局中划定了一块固定的 4KB 虚拟地址空间（通常在 0x7f3ff000）专门作为单进程的抢修工作台，用完即焚（Unmap），极其高效。

- **UTOP (用户与内核的绝对楚河汉界)**

  - 在实现 sys_mem_alloc、sys_mem_map 等函数时，必须有一个前提：**用户传入的虚拟地址 va 必须 < UTOP**。
  - 为什么？UTOP（通常是 0x7f400000）之上，是 UENVS 和 UPAGES（只读映射），再往上就是 UVPT 以及真正的内核空间 kseg0。如果恶意程序传入一个内核空间的地址请求 sys_mem_alloc，而内核不做合法性校验（is_illegal_va），内核就会亲手把自己的核心代码/数据段映射给用户篡改，系统瞬间被提权或击穿。

- **UXSTACKTOP (异常生命线的起点)**

  - 它是用户异常栈的栈顶。当常规栈（USTACKTOP）被设为只读并触发缺页时，如果内核把现场压在常规栈上，会引发“缺页引发缺页”的死锁。UXSTACK 永远可写、永远不参与 COW，它是进程在绝境中唯一可以依靠的抢修生命线。

  ### **Thinking 4.1：系统调用的实现**
  
  1. **内核在保存现场时如何避免破坏通用寄存器？**
     - **回答**：内核利用了 MIPS 寄存器约定的特殊性。硬件进入异常时，内核首先使用 $k0 和 $k1 寄存器（这两个寄存器被编译器和汇编约定保留给内核使用，用户程序不应使用它们）。通过 $k0 找到当前进程的内核栈，然后利用汇编宏 SAVE_ALL，将所有通用寄存器依次压入内核栈中的 Trapframe 结构中。在这个过程中，由于 $k0/$k1 是内核私有的，因此不会破坏任何用户态正在使用的通用寄存器。
  2. **系统陷入内核后可以直接从当时的 $a0-$a3 参数寄存器中得到用户调用 msyscall 留下的信息吗？**
     - **回答**：不可以。虽然 $a0-$a3 确实包含了参数，但由于进入内核后可能经过了多层汇编跳转和处理，物理寄存器的值可能已经被内核代码修改。最安全、可靠的方法是从内核栈上保存的 Trapframe 结构中读取，因为 SAVE_ALL 已经把触发 syscall 那一瞬间的寄存器值“冻结”在内存中了。
  3. **我们是怎么做到让 sys_ 开头的函数“认为”我们提供了同样的参数的？**
     - **回答**：在 do_syscall 中，我们手动解析 Trapframe，提取出保存在 regs[5] 到 regs[7]（对应 $a1-$a3）以及用户栈上的参数，然后按照 C 语言的函数调用约定，将这些值作为实参传递给 func（即具体的 sys_* 函数）。
  4. **内核处理系统调用对 Trapframe 做了哪些更改？**
     - **回答**：主要做了两处修改：
       - tf->cp0_epc += 4：将返回地址移至 syscall 指令的下一条，防止死循环。
       - tf->regs[2] = result：将内核函数的返回值存入 $v0（regs[2]），这样用户程序返回后就能从 $v0 拿到函数结果。
  
  ------
  
  
  
  ### **Thinking 4.2：envid2env 的实现细节**
  
  - **问题：为什么 envid2env 需要判断 e->env_id != envid？**
    - **回答**：因为 envs 数组是静态分配且循环使用的。env_id 的设计包含了两部分：数组下标和“版本号”。如果不检查 env_id 是否相等，而只通过 ENVX 获取下标，那么当一个旧进程被销毁，另一个新进程恰好分配在同一个数组槽位时，持有旧 ID 的进程可能非法操作新进程。这一步检查确保了 ID 的全局唯一性和安全性。
  
  ------
  
  
  
  ### **Thinking 4.3：mkenvid 函数细节**
  
  - **问题：mkenvid() 不会返回 0，结合系统调用和 envid2env 行为进行解释。**
    - **回答**：在 MOS 中，envid == 0 被约定为一个特殊的“幻数（Magic Number）”，代表“当前进程（curenv）”。在 envid2env 内部，如果传入 0，会直接返回 curenv。如果 mkenvid 允许生成 ID 为 0 的进程，就会导致逻辑歧义：内核无法区分用户是想操作“ID 为 0 的那个特定进程”，还是想操作“当前进程自己”。
  
  ------
  
  
  
  ### **Thinking 4.4：fork 的返回结果**
  
  - 
  - **问题：关于 fork 函数的两个返回值，说法正确的是？**
    - **回答**：**C**。fork 只在父进程中被调用了一次（用户态调用），但由于它克隆了整个进程现场，导致父子进程都会从同一个 syscall 返回点继续执行，从而在两个进程中各产生一个返回值。
  
  ------
  
  
  
  ### **Thinking 4.5：用户空间的保护（UXSTACK 与 UVPT）**
  
  1. **为什么子进程的 UXSTACK 必须重新分配，而不能共享或设为 COW？**
     - **回答**：UXSTACK 是处理写时复制异常的“案发现场”。如果 UXSTACK 也是 COW 的，那么当发生异常需要向 UXSTACK 压栈时，会因为尝试写入 COW 页面而再次触发异常。这会导致无限递归的异常嵌套，最终导致系统崩溃（Kernel Stack Overflow 或死锁）。
  2. **为什么不应对 UVPT/VPT/VPD 自映射区域调用 duppage？**
     - **回答**：这些区域是自映射机制生成的特殊镜像，它们反映的是当前进程的页表结构。如果对它们进行 duppage 或 COW 标记，会破坏 MMU 查表的递归逻辑，导致进程无法正确访问或修改自己的页表。
  
  ------
  
  
  
  ### **Thinking 4.6：vpt 与 vpd 的使用**
  
  1. **作用及用法**：它们是用户态访问页表的“窗口”。vpt[i] 获取第 i 个页表项，vpd[i>>10] 获取页目录项。
  2. **存取原理**：基于页表自映射。内核在创建进程时，将页目录本身的物理地址填入了页目录的一个条目中。
  3. **自映射体现**：页目录既是目录，也被当成了一张页表。
  4. **能否修改**：**不能**。虽然可以读取，但在用户态下，对应的页表项通常被映射为只读（没有 PTE_D 位），修改会触发异常。
  
  ------
  
  
  
  ### **Thinking 4.7：页写入异常——内核处理**
  
  1. **“异常重入”何时发生？**
     - **回答**：当用户态异常处理函数 cow_entry 正在执行时，如果它访问的内存（比如正在拷贝的页面或它自己的栈）恰好也触发了 TLB Mod 或 TLB Miss 异常，就会发生重入。
  2. **内核为什么需要将异常现场复制到用户空间？**
     - **回答**：因为内核需要保持“无状态”以支持多个进程并发。为了让用户态处理函数能够完成“抢修”并最终恢复到最初的出错点，它必须拿到发生异常那一刻的完整寄存器快照。
  
  ------
  
  
  
  ### **Thinking 4.8：页写入异常——用户处理的优势**
  
  - **问题：用户态处理相比内核态处理有什么优势？**
    - **回答**：符合微内核的设计哲学——**机制与策略分离**。内核只负责转发异常（机制），而具体的内存管理策略（如 COW、按需加载、分布式内存共享等）可以在用户态实现。这样不仅减小了内核体积，提高了系统的稳定性和灵活性，也方便开发者自定义特殊的内存行为。
  
  ------
  
  
  
  ### **Thinking 4.9：设置处理函数的顺序**
  
  - **问题：为什么先设置处理函数再进行 COW 保护？**
    - **回答**：如果在设置处理函数（sys_set_tlb_mod_entry）之前就标记了 COW，那么紧接着的任何写入操作都会触发 TLB Mod 异常。由于此时内核不知道该跳转到哪个用户函数，系统会因为找不到处理程序而 Panic。先注册处理程序是为了确保“陷阱”布下后，随时都有“诱捕器”在待命。
  
  

[^1]: `duppage`函数没有显式读取内存，不代表C编译器或者以后的多线程不会向addr写入数据，例如压栈就是一种隐式内存读取。
