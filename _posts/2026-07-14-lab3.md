Lab3的主要流程，讲解操作系统如何创建，管理与感知进程的。操作系统通过进程控制块感知进程，通过队列调度这些控制块并调度他们的运行。

操作系统通过一个结构体：进程控制块控制进程。

## 重要数据结构

1. `include/env.h`：进程控制块PCB，`struct Env`；

包括重要字段：

- **env_tf (Trapframe)**：进程上下文。当进程被中断打断陷入内核时，CPU 所有的通用寄存器、程序计数器（EPC）、状态寄存器（Status）都会保存在这里。恢复运行时，内核将这些值写回 CPU。
- **env_pgdir**：页目录虚拟地址。它是进程私有虚拟地址空间的根节点。
- **env_id / env_parent_id**：进程及其父进程的标识符。
- **env_asid**：地址空间标识符。填入 CPU 的 TLB 中，用于在不刷新 TLB 的情况下区分不同进程的相同虚拟地址。
- **env_status**：进程生命周期状态。主要有 ENV_FREE（未分配）、ENV_RUNNABLE（就绪/运行中）、ENV_NOT_RUNNABLE（阻塞）。
- **env_pri**：调度优先级。在时间片轮转中，它决定了进程一次能分配到多少个时钟周期的执行时间。

2. 全局变量：

- **`envs`**：大小为 `NENV` 的静态数组，存放系统中所有的 PCB 结构。
- **`env_free_list` (LIST)**：空闲队列。串联所有状态为 ENV_FREE 的 PCB
- **`env_sched_list` (TAILQ)**：调度队列。串联所有状态为 ENV_RUNNABLE 的 PCB，利用双端队列的特性实现队头取人和队尾放人。
- **`curenv`**：指向当前正在 CPU 上执行的进程的 PCB。
- **`cur_pgdir`**：当前活动进程的页目录地址。TLB Miss 异常发生时，底层汇编读取它来查找页表。

### 函数调用关系

内核初始化时，操作系统会调用一系列函数初始化进程的管理。此后，用户态进程会在操作系统的监督下进行并发并行的运行。也就是说，本次lab3主要涉及两条调用关系路线。

#### 内核初始化

这是系统开机后、第一个用户进程运行前的流程，完全在**内核态**、**关中断**的环境下执行。

```
mips_init()  [内核主函数]
 ├── mips_vm_init()       -> Lab 2 初始化
 ├── env_init()           -> Lab 3 初始化
 │    └── map_segment()
 ├── env_create()         -> 创建用户进程 1
 │    ├── env_alloc()
 │    │    ├── asid_alloc()
 │    │    └── env_setup_vm()
 │    ├── load_icode()
 │    │    └── elf_load_seg()
 │    │         └── load_icode_mapper()
 │    └── TAILQ_INSERT_TAIL()
 ├── env_create()         -> 创建用户进程 2
 └── kclock_init()        -> 开启硬件时钟，等待第一次中断
     (陷入死循环，等待)
```

#### 时钟中断与调度

当硬件时钟触发，打断当前正在运行的用户进程时，软硬件交接的流程。

```text
(User Process Running)
       ↓
[Hardware Timer Interrupt] -> 跳转到 0x80000180，进入内核态
```

## 调用解读

### 初始化

`mips_init`全局入口调用lab2中虚拟内存初始化之后，调用函数`env_init()`初始化进程管理。`env_init`定义在`kern/env.c`，其职责是初始化内核进程管理机制。

`env_init()`初始化`env_free_list`和`env_sched_list`，分别用于标记空闲PCB和标记调度中的PCB。然后遍历全局数组`envs[]`将其中所有块加入`env_free_list`，并标记为`ENV_FREE`。

在每个进程的虚拟地址空间中，我们预留了特定的区域（UPAGES 和 UENVS），通过页表将内核中维护物理页信息的 pages 数组和维护进程信息的 envs 数组，直接映射到这些虚拟地址上，标记为“不可写|有效|全局”。因此用户态可以访问全局的物理页信息与进程信息，但不可写。

```text
 o      ULIM     -----> +----------------------------+------------0x8000 0000-------
 o                      |         User VPT           |     PDMAP                /|\
 o      UVPT     -----> +----------------------------+------------0x7fc0 0000    |
 o                      |           pages            |     PDMAP                 |
 o      UPAGES   -----> +----------------------------+------------0x7f80 0000    |
 o                      |           envs             |     PDMAP                kuseg
 o  UTOP,UENVS   -----> +----------------------------+------------0x7f40 0000    |
 o  UXSTACKTOP -/       |     user exception stack   |     PTMAP                 |
 o                      +----------------------------+------------0x7f3f f000    |
 o                      |                            |     PTMAP                 |
 o      USTACKTOP ----> +----------------------------+------------0x7f3f e000   \|/
```

为此，`env_init`首先申请一个页面并给予全局`base_pgdir`，作为页目录。接着调用函数`map_segment`将地址批量映射为虚拟地址。`map_segment`使用`page_insert`添加映射。

```c
	base_pgdir = (Pde *)page2kva(p);
	map_segment(base_pgdir, 0, PADDR(pages), UPAGES,
		    ROUND(npage * sizeof(struct Page), PAGE_SIZE), PTE_G);
	map_segment(base_pgdir, 0, PADDR(envs), UENVS, ROUND(NENV * sizeof(struct Env), PAGE_SIZE),
		    PTE_G);
```

其中，`PADDR`宏将kseg0内核虚拟地址减去`ULIM`返回物理地址，如果您没忘记的话。

`map_segment`函数检查`pa,va,size`是否是按照`PAGE_SIZE`对齐，然后遍历所有页，使用`page_insert`将传进去的（UPAGES与UENVS）虚拟地址映射到`pages`和`envs`的物理地址。

### `env_alloc`

```c
int ret = env_alloc(&e,0);
if (ret < 0) panic("env_create: env_alloc failed");
```

`env_alloc`函数从空闲进程控制块链表（`env_free_list`）中取出一个空闲进程，初始化该进程的虚拟内存并填入一些表项。

#### `env_setup_vm()`

该函数首先分配一个页作为进程页目录，然后执行

```c
	memcpy(e->env_pgdir + PDX(UTOP), base_pgdir + PDX(UTOP),
	       sizeof(Pde) * (PDX(UVPT) - PDX(UTOP)));
```

这个`UTOP`是哪里来的？

```text
 o      ULIM     -----> +----------------------------+------------0x8000 0000-------
 o                      |         User VPT           |     PDMAP                /|\
 o      UVPT     -----> +----------------------------+------------0x7fc0 0000    |
 o                      |           pages            |     PDMAP                 |
 o      UPAGES   -----> +----------------------------+------------0x7f80 0000    |
 o                      |           envs             |     PDMAP                 |
 o  UTOP,UENVS   -----> +----------------------------+------------0x7f40 0000    |
 o  UXSTACKTOP -/       |     user exception stack   |     PTMAP                 |
 o                      +----------------------------+------------0x7f3f f000    |
 o                      |                            |     PTMAP                 |
 o      USTACKTOP ----> +----------------------------+------------0x7f3f e000    |
 o                      |     normal user stack      |     PTMAP                 |
 o                      +----------------------------+------------0x7f3f d000   \|/
```

虚拟地址`0x7f40 0000`处是用户异常栈栈顶，此处是用户栈的最大地址，上方是内核暴露的`UENVS`与`UPAGES`。也就是说，`env_setup_vm`函数将会在页目录中，把全局页目录`base_pgdir`中`UTOP`到`UVPT`的页表地址都复制过来。

最后，这个页目录放在哪里？我们使用了**自映射机制**：

```c 
	e->env_pgdir[PDX(UVPT)] = PADDR(e->env_pgdir) | PTE_V;
```

 `e->env_pgdir`在这里是内核虚拟地址，位于 kseg0 段（`page2kva`）。转换后该地址指向页目录所在的物理内存页，这个物理地址被写入页目录的第 `PDX(UVPT)` 项，并设置有效位 `PTE_V`，实现**页目录自映射**。

#### 自映射到底是什么

**查查表的过程**

操作系统地址映射有两个视角，一个是MMU两次查表的动态查表视角，一个是虚拟地址映射到物理地址的静态映射视角。在动态视角中，查表必须经历查页目录和查页表阶段。

要访问某个**页表页**（即存放页表项的物理页），通常需要两步：

1. 先通过页目录项（PDE）找到该页表页的物理地址；
2. 再在该页表页中，通过页表项（PTE）找到最终目标物理地址。

这个过程能工作的**前提**是：页表页本身已被映射到虚拟地址空间，并且页目录中对应的 PDE 正确指向该页表页的物理地址。

那么，如果我们想访问**页目录页**本身呢？直觉上，似乎需要先查页目录找到某个“页表页”，再从这个页表页中查回页目录的物理地址——但这是行不通的。

原因在于：页目录页的物理地址**从未出现在任何页表项（PTE）中**。它只出现在页目录项（PDE）里，而 PDE 是内核在创建进程时设置的，内核可以通过 `env->pgdir` 直接访问页目录页。然而，用户程序无法看到这些 PDE 背后的物理页，因为页目录页本身并没有被映射到用户虚拟地址空间中。所以，用户态下无法通过普通的页表查询方式访问页目录页。

**如何暴露页目录？**

大多数操作系统不会暴露页表给用户态，因为你无法信任用户程序。但是我们正在编写一个操作系统，将进程页目录与页表暴露出来是很有必要的。MOS有一个区域名叫`UVPT`，这一区域负责暴露该进程的页目录与页表。

我们意识到，从物理页的视角来看，页目录和页表本质上并无不同之处。页表和页目录都是具有表项的表，页表和页目录的项的格式都遵循：

```text
 31            22 21            0
+----------------+--------------+
|      PFN       |    Flags     |
|    (20 bits)   |  (12 bits)   |
+----------------+--------------+
```

所以，为了暴露页目录，我们将页目录这一物理页**伪造**成一个页表页。那么，页目录就有责任将自己这一页的物理地址视为一个页表页的地址保存起来。虚拟地址中`UVPT`的地址是`0x7fc0 0000`，取高十位，`PDX(UVPT)`，也就是第511项。MMU查表的时候，会查询第511项页目录，因此**第511项页目录项将会填写为页目录页自己的物理地址**。

这就是自映射。

一个重要的问题是，页目录虽然把自己当作是一个页表，但他既然没有被映射到虚拟空间，那么在虚拟空间中就不是一个页！自映射将页目录物理页“伪装”成一张页表页，那么 MMU 进行地址转换时，第一次查完页目录项之后会把页目录当作（二级）页表来解读，此时还没查完呢。既然我们的目的是要读取第`i`个PDE，那么为了让 MMU 能够正确索引到页目录，我们还需要让 `i` 成为**页表索引（PTX）**，而不是简单的字节偏移。访问第i个页表物理地址的虚拟地址将会是`va=UVPT+i<<12`。

进一步地，访问任意一个`va`的页表项，即第`PDX(va)`页目录项，第`PTX(va)`页表项的页表项，其虚拟地址就是

```text
vPTE	= 	UVPT + 			(PDX(va) << 12) 	+ (PTX(va) << 2)
虚拟地址 	自映射到页目录物理页 伪造第PDX(va)页表偏移	伪造第PTX(va)页表项
```

其中 
`PDX(va) = (va >> 22) & 0x3FF` 
`PTX(va) = (va >> 12) & 0x3FF`

如果您还没理解，我们重新讲解一次。首先，将`vPTE`的最高10位置为`UVPT`，这样`MMU`第一次查页目录将会前往页目录自映射的物理地址，从而将页目录视为一个页表页检查；然后，`MMU`第二次检查页目录（作为页表页），使用`vPTE`的`PTX`进行偏移，即偏移`PDX(va)`个页目录项前往真正页表页的地址；最后，在页表页返回第`PTX(va)`个页表项。

等价于：

```text
vPTE = UVPT + ((va >> 12) << 2)
```

反过来，如果您知道了`vPTE`，那么`UVPT=(vPTE|vPTE<<10)`。

#### 继续分配

`env_alloc`接着填写了进程中的数个字段，包括：

- `env_user_tlb_mod_entry`：用于COW和异常相关的处理，lab4用的
- `env_runs`：统计进程用了多少次，lab6用的
- `env_id`：进程的`pid`
- `env_asid`：进程的地址空间标识符
- `env_parent_id`：记录创建当前进程的父进程 ID
- `e->env_tf.cp0_status = STATUS_IM7 | STATUS_IE | STATUS_EXL | STATUS_UM`：始化进程的 **MIPS CP0 Status 寄存器** 值，该寄存器控制中断、异常、内核/用户模式等。
  - `STATUS_IM7`：只允许时间中断（IM7）[^2]
  - `STATUS_IE`：全局中断使能（Interrupt Enable）。
  - `STATUS_EXL`：异常级别，置 1 表示处于异常处理状态，此时 CPU 不会响应新的异常，并且 `ERET` 指令会清空该位并返回用户态。
  - `STATUS_UM`：用户模式，置 1 表示 `ERET` 后 CPU 进入用户态（否则仍为核心态）。
- `e->env_tf.regs[29] = USTACKTOP - sizeof(int) - sizeof(char **)`：设置进程的栈指针`sp`，减去 `sizeof(int)` 和 `sizeof(char **)` 是为了在栈顶预留空间，用于存放 `argc` 和 `argv`（后续 `main` 函数的参数，真希望您看过用户程序的main函数）。

最后把进程从空闲块中移出来，这已经不是一个空闲进程控制块了。并将分配的新PCB指向进程块`e`。`env_alloc()`至此结束生命周期。

特别地，EXL寄存器行为有些独特：

> Exception Level. 
>
> Set by the processor when any exception other than a Reset, Soft Reset, or NMI exception is taken. 
>
> 0:   normal level 1:   exception level 
>
> When EXL is set: The processor is running in kernel mode. Interrupts are disabled. 
>
> Read/ Write R/W Reset State Undefined In the 4Kc core, TLB refill exceptions use the general exception vector instead of the TLB refill vector. 
>
> EPC is not updated if another exception is taken.

更多有关`STATUS`寄存器相关的内容，详见后续异常与中断以及《MIPS 4KC》文档第87页。

#### `load_icode()`

进程已经就绪，但是进程仅仅是一个空白模板。需要**将 ELF 可执行文件中的代码段、数据段等内容加载到进程的用户地址空间中**，为了加载程序映像代码，我们调用了`load_icode`函数，指加载Image。

> load_icode 函数负责加载可执行文件 binary 到进程 e 的内存中。它调用的 elf_from 函 数完成了解析ELF 文件头的部分，elf_load_seg 负责将 ELF 文件的一个 segment 加载到内 存。

`load_icode()`函数具体内容比较简单：遍历ELF文件，将PT_LOAD的程序头全部加载，然后把cp0中的EPC寄存器设置为ELF文件头中存储了的程序入口。但是实现并不那么简单。

涉及的函数包括

```c
// lib/elfloader.c
const Elf32_Ehdr *elf_from(const void *binary, size_t size);
int elf_load_seg(Elf32_Phdr *ph, const void *bin,
elf_mapper_t map_page, void *data);

// kern/env.c
static void load_icode(struct Env *e, const void *binary, size_t size);
static int load_icode_mapper(void *data, u_long va, size_t offset,
u_int perm, const void *src, size_t len);
```

函数调用关系为

```text
  load_icode()
    └── elf_from()
    └── elf_load_seg()
         └── load_icode_mapper()
```



`elf_from`函数很简单，其检查`elf`合法性之后返回一个`elf`头。

>  在 Lab3 阶段，我们还没有实现文件系统，因此无法直接操作磁盘中的 ELF 文件。在这里我们已经将 ELF 文件内容转化成了 C 数组的形式（可以在 make 后查看 user/bare/loop.b.c 文件），这样可以通过编译到内核中完成加载

`elf_load_seg`函数遍历这个数组中的每一个程序头表并使用回调函数将所有`p_type`等于`PT_LOAD`的段加载映像。

> load_icode 函数会从 ELF 文件中解析出每个segment 的段头 ph，以及其数据在内存中的 起始位置bin，再由 elf_load_seg 函数将参数指定的程序段（program segment）加载到进程 的地址空间中。

`elf_load_seg`声明如下

```c
int elf_load_seg(Elf32_Phd *ph, const void *bin, elf_mapper_t map_page, void*data);
```

它负责具体的加载一个单独页。

> elf_load_seg 函数会从 ph 中获取 va（该段需要被加载到的虚地址）、sgsize（该段在内存中的大小）、bin_size（该段在文件中的大小）和 perm（该段被加载时的页面权限），并根据这些信息完成以下两个步骤： 
>
> 第一步 加载该段的所有数据（bin）中的所有内容到内存（va）。 
>
> 第二步 如果该段在文件中的内容的大小达不到为填入这段内容新分配的页面大小，即分配了新的页面但没能填满（如.bss区域），那么余下的部分用 0来填充。

`load_icode_mapper()`作为函数指针传入进去， 充当回调函数`map_page`。

最后设置`  e->env_tf.cp0_epc = ehdr->e_entry;`，设置进程程序入口。进程开始运行。

### 中断与异常分发


> 在mips体系结构中，中断、陷阱、系统调用和任何可以中断程序正常执行的情况都称作异常。mips的异常是精确异常，在发生任何异常时都指向一条指令，所有这条异常指令之前的指令都执行完成了，所有这条指令之后的指令都还没开始执行。[^3]

在计算机组成课程中，我们学习了处理器发生异常该如何处理。有的处理器会“忽视”异常，这当然会导致运行出现问题。我们的P7中，异常出现后，程序将会跳转到一个固定地址。这个固定地址就是异常处理程序。操作系统会判断到底是什么暂时阻止了程序的运行并根据情况做相应的“分发”。

在MOS中，异常发生后，CPU向协处理器报告自己的状态，将一些重要信息发送给CP0。CP0协处理器中包含相当多的寄存器，涉及lab3中断与异常向量处理的只有这几个：

| 寄存器助记符 | CP0 寄存器编号 | 描述                                                         |
| ------------ | -------------- | ------------------------------------------------------------ |
| BadVAddr     | 8              | 当发生地址错异常（Address Error）或页表缺失（TLB Miss）时，硬件自动将引发故障的虚拟地址记录于此。[^4] |
| Status       | 12             | 状态寄存器，包括中断引脚使能、其他 CPU 模式等位域。          |
| Cause        | 13             | 记录导致异常的原因。                                         |
| EPC          | 14             | 异常结束后程序恢复执行的位置。                               |

- BadVAddr寄存器在一切地址异常的时候会把引发异常的虚拟地址记录在此。不过，如果是访存时出现的错误，他也会把访存的地址存储在这里。
- Status寄存器，我们已经在上面讲过了几个重要位置，特别是`IE`, `EXL`, `ERL`和`DM`位

> Interrupt Enable: Interrupts are enabled when all of the following conditions are true: 
>
> - IE = 1, Interrupt Enable Bit 
>
> - EXL = 0, Exception Level
>
> - ERL = 0, Error Level
>
> - DM = 0, Debug Mode
>
> If these conditions are met, the settings of the IM and IE bits enable the interrupt.
>
> Operating Modes: If the DM bit in the Debug register is 1, the processor is in debug mode. Otherwise the processor is in either kernel or user mode. The following CPU Status register bit settings determine user or kernel mode. 
>
> - User mode: UM = 1, EXL = 0, and ERL = 0
>
> - Kernel mode: UM = 0, or EXL = 1, or ERL = 1 
>

- **EXL**：异常级别。异常时硬件置位，强制内核模式并禁止中断，直到软件重新配置特权级和中断屏蔽。
- **ERL**：错误级别。类似EXL，用于错误（如总线错）场景，同样禁止所有中断。
- **IE**：全局中断使能。仅当EXL=0且ERL=0时有效，否则中断被屏蔽。
- **BEV**：启动时异常向量。
  - 1：使用kseg1的异常入口（ROM，可启动）；
  - 0：使用kseg0的异常入口（RAM，正常运行时）。
- **IM7-0**：中断屏蔽。每位对应一个中断源（6个外部/板级信号 + 2个软件可写位），置1时允许该源触发异常。

Cause寄存器中的ExcCode记录了异常发生的原因。此后，操作系统软件开始负责程序异常的处理。

#### 开始异常

`.section.text.exc_gen_entry`定义了异常入口所在的代码段，调用`SAVA_ALL`宏[^5]将全部通用寄存器保存到当前栈（内核栈，`KSTACKTOP`）的 `pt_regs` 结构中，以便异常返回时恢复。

接着读取 `Status` 寄存器到 `t0`，清除三个标志位并写回：

- `STATUS_UM`：置 0 表示切换到**内核模式**。
- `STATUS_EXL`：清 0 表示**退出异常级别**，允许后续发生**嵌套异常**（硬件会重新设置 `EXL` 并更新 `EPC`）。
- `STATUS_IE`：清 0 表示**关闭所有中断**，防止在处理异常时被硬件中断打断（或根据设计稍后由软件主动开启）。

最后，读取Cause 寄存器并跳转到`exception_handlers`数组.

#### 异常向量

`kern/traps.c`中的`exception_handlers`数组存储了中断处理程序的地址。进入异常初始化程序后，程序就会根据异常向量地址跳转到相应的处理函数。

#### 时钟中断

时间中断发生，异常中断向量判断当前为中断异常进入`handle_int`，并使用`ret_from_exception`恢复现场。

函数`handle_int`定义在`genex.S`，它使用宏定义了中断处理。

```mips
NESTED(handle_int, TF_SIZE, zero)
	mfc0    t0, CP0_CAUSE
	mfc0    t2, CP0_STATUS
	and     t0, t2
	andi    t1, t0, STATUS_IM7
	bnez    t1, timer_irq
	# 这里对pending做了个位与，以此显示拓展性，实际上我们根本不会拓展这里
timer_irq:
	li      a0, 0
	j       schedule
END(handle_int)
```

其中`t0`和`t2`位与，Status 寄存器中的中断屏蔽位（IM[7:0]）指示哪些中断源被允许，Cause 寄存器中的 `IP[7:0]` 位指示当前哪些中断处于 pending 状态。两者按位与后，只有**既 pending 且未被屏蔽**的中断位会被保留在 `t0` 中。

如果检查通过，则进入调度器开始调度。调度器是不会返回的，因此我们使用`j schedule`。

#### 调度函数

有关时钟的更多信息可以参考指导书，似乎往届考察时钟的内容并不多，每次exam都是考察调度算法实现。

> `handle_int` 函数的最后跳转到了 `schedule`函数。这个函数在 `kern/sched.c` 中所定义，它 就是我们本次实验最后要写的调度函数。调度的算法很简单，就是时间片轮转的算法。
>
> 上文提到， MOS 中的时间片的长度是用时钟中断衡量的，即时间片长度被量化为 `N × TIMER_INTERVAL`。
>
>  具体的，env中的优先级即为这里的 N，规定了该进程的时间片长度。
>
> 不过寻找就绪状态进程不是简单遍历所有进程，而是用一个调度链表存储所有就绪（可运行）的进程，即一个进程在调度 链表中当且仅当这个进程是就绪（`ENV_RUNNABLE`）状态的。
>
> 当内核创建新进程时，将其插入调度链表的头部；在其不再就绪（被阻塞）或退出时，将其从调度链表中移除。

指导书讲解得很明白，我们重点讲解几个变量：

1. **`*e`**：

该变量被初始化为`curenv`，用于指出当前当前正在运行（实际上就是调度前最后一刻正在执行的算法），需要注意的是如果有抢占式算法，那么`curenv`不应当被赋值给`*e`，`*e`应当保存抢占之前的进程PCB地址。一旦抢占发生，RR算法采用`curenv`就不再可靠！必须依靠静态变量`last_rr_env`来保存上一个`rr`算法的进程。

2. 进程调度的几个标志

在RR简单时间算法中，`yield`, `count`以及`env_status`充当进程是否替换的标志。请注意，每次进入`schedule`函数，都要及时判断并更新涉及的标志变量。

3. `env_run`

函数`env_run`负责运行一个进程，它首先考虑

```c
if (curenv) {
	curenv->env_tf = *((struct Trapframe *)KSTACKTOP - 1);
}
```


将内核栈中保存的 trapframe 先保存到之前进程块自己的 env_tf 中，防止被覆盖，然后切换进程继续运行，并调用 `env_pop_tf` 把保存到进程 trapframe 弹出。

### 上机经验

#### lab3 exam

进程调度算法无非两种，抢占式算法与非抢占式算法。每年几乎都是考察抢占式算法，但是其实现与非抢占式算法并无太多不同。我们以2025与2026年为例，分别是实现EDF算法与SRTF算法。 

EDF是最早截止时间优先算法（Earliest Deadline First，EDF），该算法给每个进程分配一个“周期长度”以及“每个周期内需要运行多久”，SRTF算法是抢占式短作业优先（Shortest Remaining Time First, SRTF）。不约而同地，两种都是抢占式算法。

抢占式算法要求新建一个队列或链表，该链表需要全新的进程创建函数。因此按照题目提示，在`.h`头文件中加入新进程创建函数注册与相应的结构体、数据结构。以 `srtf` 算法为例：

```c
// include/env.h
LIST_HEAD(Env_srtf_sched_list, Env);

extern struct Env_srtf_sched_list env_srtf_sched_list; // SRTF 调度队列

struct Env *env_create_srtf(const void *binary, size_t size, int runtime);

// kern/env.c
struct Env_srtf_sched_list env_srtf_sched_list; // SRTF 调度队列

// include/env.h Env结构体中
	LIST_ENTRY(Env) env_srtf_sched_link; // 构造 env_srtf_sched_list 的链表项
	u_int env_total_runtime; // SRTF 调度参数：进程总共需要运行的时间片
	u_int env_runtime_left; // 进程剩余需要运行的时间片
```

接着，仿照原有`env_create`函数，创建一个新的进程创建函数，该函数应当同样按要求初始化进程中新增的字段，并将其塞进新建的进程抢占队列（链表）。

```c
// 原有函数
struct Env *env_create(const void *binary, size_t size, int priority) {
	struct Env *e;
	int ret = env_alloc(&e,0);
	if (ret < 0) {
		panic("env_create: env_alloc failed");
	}
	e->env_pri = priority;
	e->env_status = ENV_RUNNABLE;
	load_icode(e, binary, size);
	TAILQ_INSERT_HEAD(&env_sched_list, e, env_sched_link);
	return e;
}
// 新增函数
struct Env *env_create_srtf(const void *binary, size_t size, int runtime) {
    // 在函数声明中出现了新的参数，将其初始化到PCB中
    // env_alloc and if ret < 0...
    // 初始化参数
    e->env_status = ENV_RUNNABLE;
    e->env_runtime = runtime;
    e->env_runtime_left = runtime;
    // 将PCB塞进链表
    LIST_INSERT_HEAD(...);
}
```

如果是EDF算法，则需要初始化为

```c
    e->env_edf_runtime = runtime;
    e->env_edf_period = period;
    e->env_period_deadline = 0;
    e->env_status = ENV_RUNNABLE;
```

最后是重头戏，如何修改调度函数？调度函数的流程可以设定为以下几步：

```c
void schedule(int...args) {
	// 静态变量
    // 更新调度参数
    // 遍历抢占队列，符合条件则运行
    // 遍历RR队列，符合条件则运行
}
```

具体怎么实现？

首先遍历链表更新调度的参数

```c
struct Env* env;
// EDF
LIST_FOREACH(env, &env_edf_sched_list, env_edf_sched_link) {
    // 在这里更新
    if (clock == env->env_period_deadline) {
        // env->env_period_deadline 周期绝对时间更新
        // env->env_runtime_left 单个周期内剩余运行时间更新
    }
}
// SRTF不需要更新
```

接着再次遍历链表检查截止时间最小进程：

```c
// EDF Version
u_int min = -1; // 截止时间最小的进程的截止时间
struct Env *wheremin = NULL; // 截止时间最小的进程

LIST_FOREACH (env, &env_edf_sched_list, env_edf_sched_link) {
    if (env->env_runtime_left > 0) {
        if (min == -1) {
            min = env->env_period_deadline;
            wheremin = env;
        }
        else {
            if (env->env_period_deadline < min || (env->env_period_deadline == min && env->env_id < wheremin->env_id)) {
                min = env->env_period_deadline;
                wheremin = env;
            }
        }
    }
}

if (wheremin != NULL && wheremin->env_status == ENV_RUNNABLE) {
    wheremin->env_runtime_left--;
    env_run(wheremin);
}

```

SRTF算法完全一模一样：

```c
// SRTF Version
u_int min = -1;
struct Env *wheremin = NULL;

LIST_FOREACH (env, &env_srtf_sched_list, env_srtf_sched_link) {
    if (env->env_runtime_left > 0) {
        if (min == -1) {
            min = env->env_runtime_left;
            wheremin = env;
        }
        else {
            if (env->env_runtime_left < min || (env->env_runtimeleft == min && env->env_id < wheremin->env_id)) {
                min = env->env_runtime_left;
                wheremin = env;
            }
        }
    }
}

if (wheremin != NULL && wheremin->env_status == ENV_RUNNABLE) {
    wheremin->env_runtime_left--;
    env_run(wheremin);
}

```

接着，抢占式算法如果失效，即`wheremin`得到一个NULL值时，使用RR算法调度原有RR队列中的进程。把原有代码抄过来即可。

然而，题目有提示：

>  在课下代码中，我们定义 `struct Env *e = curenv`，随后对 `e` 进行了一系列的判断和操作。在本题中，为了使 RR 算法的调度行为不受 EDF 抢占的影响，你可能需要适当修改这一设计，使 `e` 的初值为**上次使用 RR 算法调度的进程**，并在必要时新增全局变量或静态变量。你无需考虑进程退出的情况，详见“评测说明”。**如果你在测试样例时遇到** `address too low` **等访问空指针引发的异常，请检查是否正确实现了这一修改。**

这是什么意思？我们使用了抢占式调度算法，如果某个算法抢占了RR队列中的进程，那么`curenv`就不再是上一个RR队列进程。必须使用一个`last_rr_env`静态变量来保存上一个RR队列，并且替换所有`curenv`出现的地方。因此我们需要两个小改动。

```c
// 来源于Kamonto的博客
if (wheremin != NULL && wheremin->env_status == ENV_RUNNABLE) {
    wheremin->env_runtime_left--;
    env_run(wheremin);
}
else {
    static int count = 0;
    static struct Env *last_rr_env = NULL; 
    struct Env *e = last_rr_env; // last_rr_env

    if (yield || count == 0 || e == NULL || e->env_status != ENV_RUNNABLE) {
        if (e != NULL && e->env_status == ENV_RUNNABLE) {
            TAILQ_REMOVE(&env_sched_list, e, env_sched_link);
            TAILQ_INSERT_TAIL(&env_sched_list, e, env_sched_link);
        }
        e = TAILQ_FIRST(&env_sched_list);
        last_rr_env = e; // update last rr env
        if (e == NULL) {
            panic("schedule: no runnable envs\n");
        }
        count = e->env_pri;
    }
    count--;
    env_run(e);
}
```

extra一般将会考察添加一个异常处理的程序，但是因为软院的同学们对异常处理不太熟悉，所以出题上十分八股。该异常的八股文大概是

2. 获取该错误指令，修改之或者修改前后某条指令，或者根据错误进行不同操作

操作上的八股大概就是：

1. 取出EPC对应的指令
2. 修改指令或偏移的指令
3. 按照题目自定义操作

取出EPC的操作是个超级八股的操作！老学长Kamonto的方法（他自述完全可以把这一段代码抄下来带进考场，毕竟是开卷）

```c
u_int badva = tf->cp0_epc; // 获取虚拟地址
Pde *pgdir = curenv->env_pgdir; // 获取页目录的基地址
struct Page *p = page_lookup(pgdir, badva, NULL); // 查找虚拟地址所在的页
u_int badpa = page2pa(p) + (badva & 0xfff); // 转换为物理页地址加上的页内偏移部分

u_int code = *badk0va; // MIPS 指令的内容
```
