### 实验报告总结要点

在本次实验（Lab6 管道与 Shell）中，我们探索并实现了操作系统级进程间通信（IPC）的典型方式——**管道**，以及用户态核心交互程序——**Shell**。以下为本次实验的核心设计与实现要点总结：

1. **共享页面机制（`PTE_LIBRARY`）的运用**  
   管道在底层本质上是驻留在内存中的虚拟文件。通过在 `fork` 或 `spawn` 时保持对带有 `PTE_LIBRARY` 标记的物理页面的共享映射，父子进程能够共同读写同一片物理内存（`struct Pipe`），从而实现数据的无拷贝传递。

2. **环形缓冲区的协同读写**  
   管道读写基于一个环形缓冲区（`p_buf`），通过读指针 `p_rpos` 和写指针 `p_wpos` 进行同步。当缓冲区为空或满时，进程通过系统调用 `syscall_yield()` 主动放弃 CPU，以等待另一端进程写入或读取数据。

3. **并发环境下的进程竞争及其消除**  
   在抢占式微内核系统中，非原子性的用户态包装函数（如 `dup` 和 `close`）容易受到时钟中断的影响。实验通过：
   * **控制重映射顺序**：在 `pipe_close` 中先解除 `fd` 页映射再解除 `pipe` 数据页映射；在 `dup` 中相反，先映射 `pipe` 再映射 `fd`。这确保了在不完整的中间状态下，页引用计数满足 `pageref(pipe) > pageref(fd)`，从而消除了管道关闭状态的误判。
   * **进程切换感知**：在 `_pipe_is_closed` 中通过循环读取并对比 `env->env_runs` 的值，保证了读取引用计数时数据的有效性，避免了“脏读”引发的退出异常。

4. **用户态程序加载（`spawn`）与控制台重定向**  
   实验实现了一个无需经历内核态直接在用户态装载 ELF 可执行文件的 `spawn` 函数，并利用文件描述符 `0`（标准输入）和 `1`（标准输出）的 `dup` 与 `close` 组合，实现了 Shell 中管道（`|`）以及输入输出重定向（`<`、`>`）的完整控制流。

### Thinking 思考题解答

#### **Thinking 6.1 如果不关闭自己不会用到的管道端会怎么样？**
如果进程不关闭自己不使用的管道端，会导致管道另一端的阻塞操作无法正常结束。
* 对于**读者**：如果写端的文件描述符没有被全部关闭（包括读者进程自身保留的、未关闭的写端描述符），即使其他所有的写者进程都已经退出，管道的写端引用计数仍大于零。此时读者读到缓冲区末尾时，`_pipe_is_closed` 会判断写端未关闭，导致读者无限期阻塞在 `syscall_yield()`。
* 对于**系统资源**：未关闭的无用描述符会造成文件描述符（`Fd` 结构体）及相关物理内存页面的泄露。

#### **Thinking 6.2 如果现在想让父进程作为“读者”，子进程作为“写者”，代码应当如何修改？**
应当调换父子进程中关闭端口与读写操作的逻辑。修改后的示意代码如下：
```c
switch(fork()) {
    case -1:
        break;
    case 0: /* 子进程 - 作为写者 */
        close(fildes[0]); /* 关闭不用的读端 */
        write(fildes[1], "Hello world\n", 12); /* 向管道写数据 */
        close(fildes[1]); /* 关闭写端 */
        exit(EXIT_SUCCESS);
    default: /* 父进程 - 作为读者 */
        close(fildes[1]); /* 关闭不用的写端 */
        read(fildes[0], buf, 100); /* 从管道读数据 */
        printf("parent-process read: %s", buf);
        close(fildes[0]); /* 关闭读端 */
        exit(EXIT_SUCCESS);
}
```

#### **Thinking 6.3 MOS 中的管道缓冲区大小 `PIPE_SIZE` 过小有什么影响？缓冲区大小是如何影响吞吐和切换效率的？**
* **影响**：如果 `PIPE_SIZE` 过小，当写入稍微大一点的数据时，写者极易填满缓冲区并被迫调用 `syscall_yield()` 挂起，等待读者读取；同样，读者也容易因缓冲区迅速被读空而挂起。
* **吞吐与切换效率**：
  * **较小的缓冲区**：会导致读者与写者进程之间频繁发生进程上下文切换（Context Switch）。切换带来的调度开销会显著降低系统的实际有效吞吐量。
  * **较大的缓冲区**：可以允许写者和读者一次性连续写入/读取更多字节，减少了因阻塞引起的调度次数，提高了吞吐量与切换效率。但过大的缓冲区会占用更多的物理内存。

#### **Thinking 6.4 恒等式 `pageref(rfd) + pageref(wfd) = pageref(pipe)` 在所有时刻都成立吗？请给出你的分析过程，如果不成立，是否会造成误判？**
**不成立。**
* **分析过程**：该等式在执行 `close` 或 `dup` 过程中会暂时失效。以 `pipe_close` 为例，关闭一个描述符涉及两次系统调用：`syscall_mem_unmap` 卸载数据页（`pipe`）和卸载描述符页（`fd`）。由于这两个系统调用在用户态是以顺序执行的方式调用的，中途可能被时钟中断打断。
  * 若先解除了 `pipe` 映射，在解除 `fd` 映射前发生切换，此时 `pageref(pipe)` 已减 1，而 `pageref(fd)` 尚未减 1。
* **是否会造成误判**：会。如果在上述不完整的中间状态下切换到了另一端的进程，另一端在执行 `_pipe_is_closed` 时会读到 `pageref(pipe) == pageref(fd)`，从而误判管道另一端已经关闭，导致进程异常退出。

#### **Thinking 6.5 结合代码模仿上述情景，分析一下我们的 `dup` 函数中为什么会出现预想之外的情况？**
在原版 `dup(oldfd, newfd)` 中，执行逻辑是先映射描述符页，再映射数据页：
1. `syscall_mem_map(..., oldfd, ..., newfd, ...)` —— 使得 `pageref(fd)` 增加 1。
2. `syscall_mem_map(..., ova, ..., nva, ...)` —— 使得 `pageref(pipe)` 增加 1。

**预想之外的情况分析**：
* 假设在步骤 1 执行完毕后、步骤 2 执行之前，产生时钟中断切换到了另一个读（或写）进程。
* 此时新映射的 `fd` 页引用计数已经增加，但 `pipe` 页的引用计数还没来得及增加。
* 另一个进程运行并调用 `_pipe_is_closed` 检查状态，在对比中会发现 `pageref(pipe) == pageref(fd)`，导致其误判另一端已被关闭而提前退出。

#### **Thinking 6.6 为什么在我们的 MOS 中，系统调用一定是原子操作呢？如果你觉得不是所有的系统调用都是原子操作，请给出反例。**
* **原理解析**：在 MOS 中，系统调用是通过触发 `syscall` 异常进入内核态执行的。MOS 内核目前设计为**非抢占式内核**（或在内核态执行时关闭了中断）。当 CPU 处于内核态执行系统调用函数（如 `sys_mem_map`）时，不会响应时钟中断进行进程切换，直至系统调用执行完毕并返回用户态。因此，单个 `syscall_` 开头的系统调用在实体执行上具有原子性。
* **反例说明**：虽然单个底层系统调用是原子的，但**用户态封装的接口**（如 `fork`、`spawn`、`close`）由于包含多个系统调用，在多次系统调用之间可以被时钟中断打断，因此**不是**原子的。

#### **Thinking 6.7 控制 `pipe_close` 中 `fd` 和 `pipe` 的 `unmap` 顺序，是否可以解决上述进程竞争问题？如果要复制的文件描述符指向一个管道，`dup` 会出现类似问题吗？**
1. **可以解决**。
   * 如果调整顺序为“先 unmap `fd`，再 unmap `pipe`”，在两个操作的间隙中，`pageref(fd)` 先减 1，此时 `pageref(pipe) > pageref(fd)`。
   * 即使在此处发生时钟中断，判定条件 `pageref(pipe) == pageref(fd)` 依然不成立，不会引发另一端误判其关闭。只有两步都完成时，等式才会成立，这正是预期的正确状态。
2. **`dup` 会出现类似问题**。
   * 在复制指向管道的文件描述符时，若先 map `fd` 再 map `pipe`，会在间隙中导致 `pageref(fd)` 暂时偏大，从而满足 `pageref(pipe) == pageref(fd)` 的误判条件。
   * **解决方法**：将顺序调整为“先 map `pipe` 数据页，再 map `fd` 描述符页”。这样在中间状态下，`pageref(pipe)` 先增加，依然保持 `pageref(pipe) > pageref(fd)`，避免了竞争。

#### **Thinking 6.8 `elf_load_seg()` 和 `load_icode_mapper()` 函数是如何确保加载 ELF 文件时，bss 段数据被正确加载进虚拟内存空间？**
* **原理分析**：BSS 段代表未初始化的全局变量，在 ELF 磁盘文件中不占用实际的存储数据空间（`p_filesz` 小于 `p_memsz`），但在程序加载到内存中时需要为其分配物理空间并清零。
* **具体实现细节**：
  1. `elf_load_seg` 内部会根据程序头中的 `p_memsz`（内存大小）来循环分配物理页面，而不仅是根据 `p_filesz`（文件数据大小）。
  2. 在加载时，首先将文件内存在的数据（大小为 `p_filesz`）从 ELF 文件中复制到分配的内存页对应偏移位置处。
  3. 对于超出 `p_filesz` 但在 `p_memsz` 范围内的内存区域（即 BSS 段），由于 MOS 在通过 `syscall_mem_alloc` 分配新页面时，内核默认会将物理页面内容清零，且在回调映射函数（如 `load_icode_mapper` 或 `spawn_mapper`）中，若遇到超出 `p_filesz` 的部分，会配合 `memset` 显式将剩余内存空间清零。由此确保了 BSS 段在内存中占有空间且初始值为 `0`。

#### **Thinking 6.9 在哪步，0 和 1 被“安排”为标准输入和标准输出？请分析代码执行流程。**
1. 系统的起始进程 `user/icode.b` 启动后，首先通过 `spawn` 创建了 `init.b` 进程。
2. 在 `user/init.c` 的 `main` 函数中，执行了如下代码：
   ```c
   opencons(); // 打开控制台设备，由于是第一个打开的文件，分配的文件描述符为 0
   dup(0, 1);  // 将 0 号描述符复制到 1 号，此时 1 号也指向控制台设备
   ```
3. 此时，`0` 成为标准输入（stdin），`1` 成为标准输出（stdout）。
4. 随后，`init.b` 进程通过 `spawn` 创建了 Shell 进程 `sh.b`。由于 `spawn` 会将带有 `PTE_LIBRARY` 权限的页面（包括文件描述符表）映射给子进程，`sh.b` 继承了这两个文件描述符。此后，所有从 Shell 启动的外部程序都会默认继承并沿用这两个标准输入输出。

#### **Thinking 6.10 在 MOS 中我们用到的 shell 命令是内置命令还是外部命令？请思考为什么 Linux 的 `cd` 命令是内部命令而不是外部命令？**
* **MOS 中的命令类型**：在 MOS 中，我们用到的命令（如 `ls.b`、`cat.b` 等）是**外部命令**。它们是独立编译并存储在磁盘/文件系统上的可执行二进制文件，Shell 需要通过 `spawn` 产生新进程来加载并运行它们。
* **Linux 的 `cd` 命令为什么必须是内置命令**：
  * 每个进程都拥有自己独立的“当前工作目录”属性。
  * 如果 `cd` 是外部命令，Shell 在执行它时必须先 `fork` 一个子进程来运行 `cd`。子进程虽然成功改变了自己的工作目录，但当它运行结束并退出后，父进程（Shell）的工作目录并没有发生任何改变。
  * 因此，为了改变 Shell 进程本身的工作目录，`cd` 必须作为内置命令由 Shell 进程自身直接调用系统调用（如 `chdir`）来执行。

#### **Thinking 6.11 在你的 shell 中输入命令 `ls.b|cat.b>motd`：**
##### **1. 可以观察到几次 `spawn`？分别对应哪个进程？**
可以观察到 **2 次** `spawn`：
1. **第一次 `spawn`**：对应 `ls.b` 进程。由负责执行管道左侧命令的子 Shell 进程调用，用于运行 `ls.b`。
2. **第二次 `spawn`**：对应 `cat.b` 进程。由负责执行管道右侧命令的子 Shell 进程调用，用于运行 `cat.b`。

##### **2. 可以观察到几次进程销毁？分别对应哪个进程？**
可以观察到 **4 次** 进程销毁：
1. **第一次销毁**：`ls.b` 进程执行完毕，自行退出并被销毁。
2. **第二次销毁**：`cat.b` 进程执行完毕，自行退出并被销毁。
3. **第三次销毁**：右侧子 Shell 进程在等待 `cat.b` 退出后执行 `exit()` 自身销毁。
4. **第四次销毁**：左侧子 Shell 进程在等待其子进程及 `rightpipe`（右侧子 Shell）退出后执行 `exit()` 自身销毁。
